# Архитектура cdekx

Документ описывает слоистую структуру библиотеки, принятые решения и то,
чем они мотивированы. Читается вместе с [`API_COVERAGE.md`](API_COVERAGE.md)
(что уже покрыто) и [`license.md`](license.md) (лицензия и происхождение кода).

## Слои

```
┌────────────────────────────────────────────────────────────────┐
│  Пользовательский код                                          │
└───────────────┬────────────────────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────────────────────┐
│  CdekClient (client.py)                                        │
│  • владение ресурсами: .orders .calculator .locations …        │
│  • жизненный цикл (async with / aclose)                        │
│  • конфигурация и выбор среды                                  │
└──────┬──────────────────────────┬──────────────────────────────┘
       │                          │
┌──────▼───────────────┐   ┌──────▼──────────────────────────────┐
│  endpoints/*         │   │  models/*  +  types/enums.py        │
│  тонкие обёртки      │   │  pydantic v2: запросы/ответы,       │
│  путь + параметры    │   │  справочники, события вебхуков      │
│  + модель ответа     │   │                                     │
└──────┬───────────────┘   └─────────────────────────────────────┘
       │
┌──────▼─────────────────────────────────────────────────────────┐
│  _http.py  HttpClient                                          │
│  • один httpx.AsyncClient (пул соединений)                     │
│  • RetryPolicy: backoff + jitter, Retry-After, повтор на 401   │
│  • Timeouts, нормализация query-параметров                     │
│  • request_raw() отдаёт БАЙТЫ: JSON парсится один раз в модели │
│  • raise_for_status → иерархия ApiError (ленивый разбор тела)  │
└──────┬─────────────────────────────────────────────────────────┘
       │
┌──────▼─────────────────────────────────────────────────────────┐
│  _auth.py  AuthProvider                                        │
│  • OAuth2ClientCredentials: кэш токена + asyncio.Lock          │
│  • StaticTokenProvider (тесты, прокси)                         │
│  • хук on_token для внешнего кэша (Redis)                      │
└────────────────────────────────────────────────────────────────┘
```

Правило зависимостей: стрелки идут только сверху вниз. `endpoints` ничего не
знают про `httpx`, `_http` ничего не знает про модели СДЭК, `types` не знает
ничего ни о ком. Благодаря этому замена транспорта или генерация моделей из
OpenAPI не затрагивают остальные слои.

## Ключевые решения

### 1. httpx вместо aiohttp

* единый API для синхронного и асинхронного кода (путь к `CdekSyncClient`);
* встроенная поддержка HTTP/2 и прокси;
* `respx` позволяет тестировать транспорт без реального сервера;
* `base_url`, `params`, `timeout` — из коробки.

`aiohttp` остаётся валидным выбором, но для SDK важнее предсказуемость и
тестируемость, чем специфика `aiohttp`.

### 2. Один клиент на всё время жизни

Новая HTTP-сессия на каждый запрос (и отдельная — на каждый запрос токена)
убивает keep-alive, добавляет TLS-handshake на каждый вызов и ломает пул
соединений под нагрузкой.

В `cdekx` `HttpClient` держит один `httpx.AsyncClient`. Клиент — контекстный
менеджер: `async with CdekClient(...) as client:`. Если контекст не подходит,
не забудьте `await client.aclose()`.

### 3. Ресурсы вместо миксинов

Клиент, собранный из миксинов, сваливает все методы в одно пространство имён:
автодополнение не помогает, конфликты имён решаются порядком наследования.

В `cdekx` каждая группа методов — класс-ресурс: `client.orders.create(...)`,
`client.calculator.tariff(...)`. Ресурсы создаются лениво и кэшируются, так
что накладных расходов нет, а читаемость и IDE-поддержка заметно лучше.

### 4. Ретраи и лимиты

СДЭК декларирует порог гарантированной обработки ~200 RPS на договор и
возвращает 429/5xx при перегрузке. `RetryPolicy` по умолчанию:

* 3 попытки, backoff `0.5 · 2^n` с джиттером, потолок 8 с;
* повторяются 408, 425, 429, 500, 502, 503, 504;
* повторяются только идемпотентные методы (GET/PUT/PATCH/DELETE) — POST
  не повторяется автоматически, чтобы не создать два заказа;
* уважается заголовок `Retry-After`;
* на 401 кэш токена инвалидируется и запрос повторяется один раз.

Для POST, которые СДЭК позволяет повторять безопасно (например, печать форм),
можно передать явный `retry=RetryPolicy(methods=frozenset({"GET","POST"}))`.

Дополнительно `max_concurrency` ограничивает число одновременных запросов
через `httpx.Limits` + `asyncio.Semaphore`.

### 5. Разбор ответов: `model_validate_json`, а не `json.loads` + `model_validate`

Тело ответа не парсится в транспортном слое. `HttpClient.request_raw()`
возвращает байты, эндпоинт отдаёт их в `model_validate_json()` /
`TypeAdapter.validate_json()` — JSON разбирается **один раз** и Rust-парсером
pydantic, без промежуточного словаря.

Замеры (`benchmarks/parse_benchmark.py`, Python 3.11, pydantic 2.14):

| payload | `json.loads` + `model_validate` | `model_validate_json` | выигрыш |
| --- | --- | --- | --- |
| конверт заказа, 1.8 КБ | 62.8 мкс | 37.4 мкс | **1.68×** |
| список 300 ПВЗ, 374 КБ | 12.6 мс | 6.8 мс | **1.86×** |

Два следствия, которые легко упустить:

1. **Выигрыш даёт только единый `validate_json` для всего массива.** Гибрид
   «Rust-парсинг JSON → поэлементный `model_validate`» замеряется в 12.9 мс —
   это *медленнее* исходного пути: Python-цикл по 300 элементам съедает всё.
2. **`json.loads` остаётся, но только там, где нужен `dict`:** тело ошибки
   (ленивый `Response.json` → `raise_for_status`) и escape hatch `misc.raw()`.
   Разделов без строгих моделей в библиотеке не осталось: все методы
   `api_v2_integration` разбираются в модели. На успешном типизированном
   ответе `json.loads` не вызывается ни разу — это зафиксировано тестом
   `test_endpoint_does_not_json_loads_entity_body`.

Цена решения — два парсера в голове: `parse_model_json`/`parse_list_json`
(байты) и `parse_model`/`parse_list` (словари). Оба живут в `endpoints/base.py`
и возвращают одинаковые модели, что проверено тестами на эквивалентность.

### 6. Ошибки как данные

`ApiError` хранит `status_code`, разобранные `errors[]` (код + сообщение +
поле), сырое `body` и `request_id` — последний нужен при обращении в поддержку
СДЭК.

Отдельная сложность — у СДЭК **две формы успешного ответа**, и обе могут
содержать ошибки при HTTP 200:

| Форма | Где встречается | База модели | Как проверять |
| --- | --- | --- | --- |
| `{entity, requests[], related_entities[]}` | заказы, заявки, печать, преалерты | `ResponseEnvelope[T]` | `envelope.state`, `envelope.errors` |
| `{errors[], warnings[], <список>}` | чеки, паспортные данные, реестры, фото документов, ограничения, доступные даты курьера | `ListResponse` | `response.has_errors`, `response.error_codes` |
| пустое тело 200 | `POST /v2/reverse/availability` | — | отсутствие `ApiError` |

Калькулятор — третий вариант: HTTP 200 с ошибками внутри (`has_errors`),
причём часть тарифов может рассчитаться, а часть нет.

### 7. Модели: `extra="allow"`

СДЭК меняет контракт несколько раз в год (см. историю изменений на
apidoc.cdek.ru). Жёсткая схема (`extra="forbid"`) ломала бы пользователей на
каждом добавлении поля. Поэтому:

* неизвестные поля сохраняются и доступны через `model.extra`;
* обязательными объявлены только действительно обязательные поля;
* `use_enum_values=True` — можно передать и `OrderType.E_COMMERCE`, и `1`;
* даты парсятся терпимо (`CdekDateTime`): формат СДЭК `+0300` не понимается
  `datetime.fromisoformat` в Python 3.10.

### 8. Справочники, которые устаревают

`TariffCode`, `ServiceCode`, `WebhookType`, `OrderStatus` объявлены как
enum'ы с известными значениями, но **типы полей допускают `int`/`str`**:
`tariff_code: TariffCode | int`. Новый код тарифа не требует релиза библиотеки.
Актуальный список тарифов по договору доступен из API:
`client.calculator.available_tariffs()` (коды доп. услуг и статусов — из
Приложений 6 и 15 на apidoc.cdek.ru, отдельных методов для них нет).

### 9. Асинхронность самого API

Создание/изменение заказа, печать форм — задачи. Ответ приходит с кодом
**202** и содержит `entity.uuid` плюс `requests[].state = ACCEPTED`.

Ключевая деталь, на которой спотыкаются интеграции: `ACCEPTED` — это состояние
**запроса**, а не сущности, и оно не гарантирует создание заказа. Обычное время
обработки 200–500 мс, при пиковой нагрузке до 30–60 с; документация рекомендует
выдержать 2–3 секунды перед первым опросом.

Метода `/v2/statuses/{uuid}` в актуальном API нет: результат узнают повторным
чтением сущности. `client.orders.wait(uuid)` опрашивает `GET /v2/orders/{uuid}`
до перехода `requests[].state` в `SUCCESSFUL`/`INVALID` (или появления
`cdek_number`), при `INVALID` выбрасывает `ApiError` с кодами ошибок СДЭК
(`v2_order_invalid`, `v2_sender_location_not_recognized`, …). Для
высоконагруженных сценариев предназначены вебхуки.

### 10. Вебхуки

СДЭК не подписывает тело вебхука, поэтому штатные средства защиты — секрет в
пути подписки и (опционально) фильтр по IP-диапазонам. `WebhookApp`
инкапсулирует это и всегда отвечает 200, если обработчик упал (иначе СДЭК
через 24 часа удалит подписку); поведение переключается флагом
`raise_on_handler_error`.

IP-фильтр **по умолчанию выключен**: `CDEK_IP_RANGES` намеренно пуст, потому что
СДЭК не публикует стабильный перечень адресов, а устаревший allowlist молча
отбросил бы легитимные события. Актуальные диапазоны выдаёт поддержка СДЭК —
их передают явно: `WebhookApp(on_event=..., ip_ranges=("192.0.2.0/24",))`.
Основная защита — секрет в пути подписки.

### 11. Логирование

Стандартный `logging` с логгерами `cdekx`, `cdekx.http`, `cdekx.auth`.
Библиотека не добавляет обработчиков и не тянет `loguru`: настройка вывода —
задача приложения.

## Расширение библиотеки

Добавление нового метода API:

1. **Модели** — `src/cdekx/models/<раздел>.py`, экспорт в `models/__init__.py`.
2. **Эндпоинт** — метод в существующем классе `endpoints/<раздел>.py`
   (или новый класс + свойство в `CdekClient`).
3. **Тест** — `tests/unit/endpoints/test_<раздел>.py` на `respx` +
   JSON-фикстура в `tests/fixtures/`.
4. **Документация** — строка в `docs/API_COVERAGE.md`, пример в `examples/`,
   запись в `CHANGELOG.md`.

### Генерация моделей из OpenAPI

СДЭК отдаёт полную OpenAPI-спецификацию. Рекомендуемый процесс:

```bash
# 1. скачать спецификацию (apidoc.cdek.ru → «Скачать OpenAPI спецификацию»)
# 2. сгенерировать черновики моделей
python scripts/generate_from_openapi.py openapi.json --out src/cdekx/models/_generated/
# 3. вручную перенести нужное в models/<раздел>.py, добавив описания и валидаторы
```

Автогенерация целиком сознательно **не** используется: сырые схемы СДЭК
содержат `additionalProperties`-мешки и нечитаемые имена, а ценность SDK —
в эргономике.

## Тестирование

| Слой | Инструмент | Что проверяется |
| --- | --- | --- |
| unit | `pytest` + `respx` | ретраи, авторизация, разбор ответов, пагинация, сериализация моделей |
| contract | фикстуры в `tests/fixtures/` | модели соответствуют реальным ответам API |
| integration | `api.edu.cdek.ru`, флаг `CDEKX_RUN_INTEGRATION=1` | реальные вызовы учебной среды (не в CI по умолчанию) |

Интеграционные тесты не должны попадать в обязательный CI: учебная среда
СДЭК нестабильна, а тестовые ключи публичны.

## Релизный процесс

1. Обновить `src/cdekx/_version.py` и `CHANGELOG.md`.
2. `make check` — все проверки зелёные.
3. Тег `vX.Y.Z` → `.github/workflows/release.yml` собирает и публикует пакет
   (рекомендуется PyPI Trusted Publisher, без токенов в репозитории).
4. SemVer: до `1.0.0` минорные версии могут менять публичный API; изменения
   фиксируются в `CHANGELOG.md`.

## License

**Apache-2.0** — см. `LICENSE` и `NOTICE`.

Почему это корректно:

* `cdekx` — независимая реализация публичного API СДЭК. Модели и пути методов
  построены по OpenAPI-спецификации apidoc.cdek.ru (`scripts/fetch_openapi.py`
  скачивает её, `scripts/generate_from_openapi.py --drift` сверяет поля моделей
  со схемами);
* исходный код других клиентов СДЭК не копировался и не перерабатывался.
  Проведённое построчное сравнение исходников не выявило заимствованных функций,
  классов, алгоритмов или докстрингов; немногочисленные совпавшие строки —
  константы справочников СДЭК (`INSURANCE = "INSURANCE"`,
  `EXPRESS_LIGHT_PICKUP = 482`);
* то, что объективно совпадает с любой другой интеграцией СДЭК, — это
  **неохраняемые авторским правом факты**: пути методов, имена полей, типы
  данных, значения справочников (коды тарифов, доп. услуг, статусов, валют).
  Авторское право охраняет форму выражения, а не идеи и факты;
* архитектура написана самостоятельно: ресурс-эндпоинты вместо миксинов,
  конверт `ResponseEnvelope` с `requests[].state` и `related_entities`,
  политика ретраев, пагинатор, ожидание асинхронных задач, ASGI-приёмник
  вебхуков.

Следствия для пользователей: библиотеку можно включать в проприетарные и
коммерческие продукты без открытия их исходного кода, патентная оговорка
Apache-2.0 включена, требования — сохранить копирайт, `LICENSE` и `NOTICE`
и отмечать существенные изменения файлов.

Если вам нужна синхронная интеграция со СДЭК — посмотрите на пакет `cdek`
(Apache-2.0, `requests` + pydantic v2, активные релизы): `cdekx` сознательно
асинхронный и синхронный клиент не предоставляет.
