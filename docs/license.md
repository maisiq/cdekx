# Лицензия и происхождение кода

`cdekx` распространяется под **Apache-2.0** — см. файлы `LICENSE` и `NOTICE`
в корне репозитория.

## Что это значит для вас

* библиотеку можно использовать в проприетарных и коммерческих продуктах без
  открытия их исходного кода;
* можно модифицировать и распространять производные работы;
* патентная оговорка Apache-2.0 включена (в отличие от MIT);
* обязательства — сохранить копирайт, текст лицензии и `NOTICE`, а также
  отмечать существенные изменения файлов (раздел 4 Apache-2.0).

## Происхождение кода

`cdekx` — независимая реализация публичного API СДЭК v2.

* Модели и пути методов построены по OpenAPI-спецификации apidoc.cdek.ru
  (секция `api_v2_integration`). Спецификация скачивается скриптом
  `scripts/fetch_openapi.py`, а расхождение полей моделей со схемами проверяется
  командой `scripts/generate_from_openapi.py --drift` (`make drift`).
* Исходный код других клиентов СДЭК не копировался и не перерабатывался.
  Построчное сравнение с доступными сторонними реализациями не выявило ни одной
  заимствованной функции, класса, алгоритма или докстринга; совпадающие строки —
  это константы справочников СДЭК (`INSURANCE = "INSURANCE"`,
  `EXPRESS_LIGHT_PICKUP = 482`, `IN_TRANSIT = "IN_TRANSIT"`) и имена, взятые
  напрямую из спецификации API (`Location`, `Money`, `Contact`, `Package`,
  `Item`, `Service`, `Order`, `City`, `Region`, `RUB`, `USD`).
* Общее с любой другой интеграцией СДЭК ограничивается неохраняемыми фактами
  о внешнем API: путями методов, именами полей, типами данных и значениями
  справочников (коды тарифов и доп. услуг, статусы, валюты, ISO-коды стран).

## Ключевые части реализации

Написаны в `cdekx` самостоятельно:

* ресурс-эндпоинты (`client.orders.*`, `client.calculator.*`) вместо миксинов
  с плоским пространством имён;
* конверт ответа `ResponseEnvelope` с `requests[].state` (ACCEPTED/SUCCESSFUL/INVALID),
  `errors`, `warnings` и `related_entities`;
* ожидание асинхронных задач API (`orders.wait()`, `client.wait_order()`) —
  не только получение UUID задачи;
* `RetryPolicy` (backoff + джиттер, `Retry-After`, повторная авторизация на 401);
* OAuth-провайдер с `asyncio.Lock` и хуком для внешнего кэша токенов;
* `Paginator` для page-based пагинации;
* иерархия исключений с кодами ошибок СДЭК (`v2_*`) и `request_id`;
* разбор ответов через `model_validate_json` без промежуточного `json.loads`;
* ASGI-приёмник вебхуков со всеми 10 типами событий;
* печатные формы до готового файла (`wait_*()` + `*_pdf()`);
* тесты (296 unit-тестов).

Там, где старая документация расходится с реальным API, `cdekx` следует
актуальной спецификации: `phones` как список объектов, `PATCH /v2/orders`
вместо `PUT /v2/orders/{uuid}`, `feacn_code`/`jewel_uin`/`marking` вместо
`tn_ved_code`/`uin`/`marking_code`, пути печати и подбор города.

Замеры разбора ответов — в `benchmarks/parse_benchmark.py`, обоснование выбора
`model_validate_json` — в
[`ARCHITECTURE.md`](ARCHITECTURE.md#5-разбор-ответов-model-validate-json-а-не-jsonloads-model-validate).

## Почему Apache-2.0, а не GPL-3.0

Изначально каркас был опубликован под GPL-3.0-or-later как перестраховка —
на случай, если проект сочтут производным от чужой GPL-реализации. После
сравнения исходников оснований для этого нет: заимствованного кода нет,
а совпадающие элементы являются фактами о внешнем API и авторским правом
не охраняются.

Apache-2.0 выбран вместо MIT из-за явной патентной оговорки — для SDK,
который подключают к коммерческим интеграциям, это полезнее.

## Синхронная интеграция

`cdekx` сознательно асинхронный. Если нужен синхронный клиент на `requests` —
посмотрите пакет [`cdek`](https://pypi.org/project/cdek/) (Apache-2.0,
pydantic v2, активные релизы). Мы не поддерживаем синхронную ветку, чтобы не
дублировать работающее решение.
